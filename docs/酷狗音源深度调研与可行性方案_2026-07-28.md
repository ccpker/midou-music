## 一、深度调研结果

### 1.1 EchoMusic × MoeKoeMusic 核心技术溯源

**关键发现：两个项目共用同一个后端！**

| 项目 | 后端 submodule | 仓库地址 | 类型 |
|------|--------------|----------|------|
| **EchoMusic** | `server/` | `github.com/MakcRe/KuGouMusicApi.git` | Node.js |
| **MoeKoeMusic** | `api/` | `github.com/MakcRe/KuGouMusicApi` | Node.js |

两个项目**不约而同**都用了 MakcRe 的 KuGouMusicApi 作为后端，区别只在于打包方式和 UI。

**EchoMusic 实际架构（与 README 描述有差异）：**
```
Electron 42 主进程
  ├── 内置 Node.js 服务（electron 主进程内嵌）
  │     └── KuGouMusicApi（子模块：概念版 API）
  ├── Vue 3.5 前端 Renderer
  └── 原生 Rust NAPI（音频处理、媒体控制）
```
它的 "官方服务器直连" 指的是 KuGouMusicApi 的服务器端直连酷狗，和米豆自研的方向一致。

**MoeKoeMusic 架构：**
```
Electron 39 主进程
  ├── 前端：Vue 3 + Vite（`npm run serve`）
  ├── 后端：内置 KuGouMusicApi（`npm run api`，端口 6521）
  └── electron-builder 打包（`dist_electron/`）
```

### 1.2 "每日自动领 VIP" 的真相

EchoMusic README 明确说"每日自动领取VIP"——这是**酷狗概念版的官方机制**，不是破解：

> "登录后概念版账号可自动领取每日VIP，登录就是VIP"

酷狗概念版给所有用户每天免费领一次 VIP 时长的福利。EchoMusic/MoeKoeMusic 帮用户自动化了这个领取过程（登录后自动调用领取接口），所以"登录就是 VIP"。

**这意味着：只要实现扫码/密码登录，就能通过概念版 API 获取 VIP 播放权限。**

### 1.3 KuGouMusicApi（MakcRe）到底能不能拿到播放地址？

这是之前测试失败的核心问题。分析失败原因：

| 测试 | 接口 | 结果 | 可能原因 |
|------|------|------|----------|
| 标准版 `/yy/index.php` | 无 token | 版权限制 20010 | 必须 VIP |
| 概念版 `/v5/url` | 无 token | 版权限制 20028 | 参数不全 |
| 概念版 `/v5/url` | 有 dfid（固定值） | 版权限制 20028 | token 无效 |
| EchoMusic 实际使用 | 完整扫码登录 | ✅ 能播放 | token 正确 |

**结论**：播放地址的版权校验在**服务端**，token 必须来自真实的账号登录流程。固定 dfid 不够——需要有完整 dfid+mid+token 的组合。

### 1.4 酷狗概念版登录接口体系

基于 EchoMusic/MoeKoeMusic 公开信息整理的登录架构：

```
设备注册 → 获取 dfid（设备唯一标识）
     ↓
账号登录（扫码/手机/密码）→ 获取 token + userid + vip_token
     ↓
每日领VIP（概念版官方接口）→ 获取当日 VIP 时长
     ↓
搜索/播放 → 用 token 请求 `/v5/url` 等接口
```

**三个登录通道（复杂度递增）：**

| 登录方式 | 复杂度 | 成功率 | 适合场景 |
|---------|--------|--------|---------|
| **扫码登录** | 低 | ✅ 高 | 桌面端首选（手机 app 扫二维码） |
| **短信验证码** | 中 | ⚠️ 需WAF | 备用 |
| **账号密码** | 高 | ❌ WAF拦截 | 不推荐 |

**扫码登录的三个步骤（纯 HTTP，无加密）：**
```
前端 GET /v2/qrcode → 获取 key + 二维码 URL
       ↓
前端用 qrcode 库生成二维码图片（用户扫码）
       ↓
前端每 2s GET /v2/get_userinfo_qrcode?key=xxx 轮询
       ↓
返回 token → 存入本地 → 登录成功
```

## 三、可行性方案（两条路径对比）

### 路径 A：自研 Rust 实现（推荐）

**核心思路**：在现有 `midou-music-v2` Rust 后端里实现酷狗概念版扫码登录，复用 KuGouMusicApi 的参数逻辑。

**优势**：
- 与 Tauri v2 原生集成，无需 Node 子进程
- 可控性强，方便调试
- 与现有 rodio 播放引擎无缝对接
- 不引入 Node.js 运行时依赖

**工作量估算**：
| 功能 | 复杂度 | 预计行数 |
|------|--------|---------|
| QR code 生成（Rust qrcode crate） | 低 | ~50 |
| 扫码状态轮询 | 低 | ~30 |
| Token 持久化 | 低 | ~50 |
| 每日 VIP 领取 | 低 | ~30 |
| 播放地址获取（含 token） | 中 | ~100 |
| 前端扫码 UI 组件 | 中 | ~150 |

**总计**：约 **400 行 Rust + 150 行 React**

**与现有代码的接口对接**：
```rust
// 新增命令（platform/kugou.rs）
pub async fn kugou_qr_key() -> Result<QrKey, KugouError>
pub async fn kugou_qr_check(key: &str) -> QrStatus  // Pending/Scanned/Expired/Token
pub async fn kugou_claim_vip(token: &str) -> Result<(), KugouError>
pub async fn kugou_play_url(hash: &str, album_id: &str, token: &str) -> Result<PlayUrl, KugouError>

// config.rs
struct KugouAuth {
    dfid: String,
    token: String,
    userid: i64,
    username: String,
    vip_expires: DateTime,
}
```

### 路径 B：嵌入 KuGouMusicApi（Node 子进程）

**核心思路**：在 Tauri 打包时，把编译好的 KuGouMusicApi Node 服务一起打包为子进程。

**优势**：
- 完全不用改登录逻辑，MakcRe 替你维护
- EchoMusic/MoeKoeMusic 验证过的方案

**问题**：
| 问题 | 影响 |
|------|------|
| Node.js 运行时打包 | Tauri 打包体积增大 ~50MB |
| 进程管理 | Node 进程不稳定（之前踩过的坑） |
| 与 Tauri 非共生 | IPC 通信增加复杂度 |
| 依赖外部库 | 需要单独维护 Node 依赖 |
| 额外维护负担 | 一个项目两套运行时 |

**结论**：路径 A 完胜，理由同 v1 的决策——**自研 Rust 不依赖 Node**。

## 五、红线与风险

| 风险 | 缓解措施 |
|------|---------|
| 酷狗接口变动（签名/参数变化） | 用 EchoMusic 实时跟踪；接口版本隔离 |
| 扫码登录轮询超时 | 5 分钟超时，显示过期提示 |
| 密码不落盘 | 只存 token，不存密码 |
| Node 打包体积 | 用路径 A（纯 Rust），规避此问题 |

**绝对红线**：不修改 `Cargo.toml` 核心依赖，不改 `lib.rs` 已有命令注册结构。
