## 三、可能的原因分析

### 对比我们的实现

| | 我们的 v2 | 现有项目（推测） |
|---|---|---|
| **search_type** | `3`（音乐区） | 可能是 `video` 或其他 |
| **Cookie** | buvid3/buvid4（实时获取） | 可能用固定 Cookie 或 Session |
| **风控策略** | 被拦截 `code=-1200` | 正常工作 |
| **更新时间** | - | 2026-02~06 都在更新 |

### 可能的解决方案

1. **search_type 改为 `video`**（之前报告里提到）
   - 优点：避开音乐区风控
   - 缺点：需要额外过滤视频（排除鬼畜/教学等）

2. **使用固定 Cookie 而非实时获取**
   - buvid 可能需要"老化"（用过一段时间的更可信）
   - 实时生成的 buvid 可能被标记为"机器人"

3. **参考 BBPlayer/bili-music 的源码**
   - 直接看他们怎么调 API
   - 复制他们的参数/Header

4. **使用 WBI 签名**（之前报告提到，但说搜索不需要）
   - 可能 B站升级了风控，现在搜索也需要签名

## 四、关键发现（2026-07-27 16:30）

### v1 vs v2 对比

| 项目 | v1 | v2 | 差异 |
|------|----|----|------|
| search_type | `3`（音乐区） | `video`（已改） | v2 已修改 |
| Cookie | 固定（buvid3=infoc, b_nut=1） | 实时获取 buvid3/buvid4 | **关键差异** |
| WBI 签名 | ❌ 无 | ❌ 无 | 都缺失 |
| 完整 Header | 简单 | 完整（Origin/Sec-Fetch-*） | v2 更完整 |
| 状态 | ❓ 未知 | ❌ code=-1200 | v2 被拦截 |

### 测试：直接访问 API

```
GET https://api.bilibili.com/x/web-interface/search/type?search_type=3&keyword=晴天
→ 返回 412（安全风控）
```

**结论**：B站现在对无 Cookie 的请求做了风控，必须带 Cookie 才能访问。

## 五、B站扫码登录调研（2026-07-27 16:32）

### 登录流程（完整）

```
1. GET /x/passport-login/web/qrcode/generate
   → 返回 qrcode_url + qrcode_key

2. 轮询 GET /x/passport-login/web/qrcode/poll?qrcode_key=xxx
   → code=0 表示成功
   → 返回 SESSDATA、bili_jct、DedeUserID

3. GET /x/passport-login/web/crossDomain?...
   → 获取最终登录 Cookie
```

### 登录后能力

| 功能 | 零登录 | 登录后 |
|------|--------|--------|
| 搜索 | ✅（但受风控） | ✅ |
| 播放 | ✅ | ✅ |
| 收藏夹 | ❌ | ✅ |
| 关注 UP主 | ❌ | ✅ |
| 评论/弹幕 | ❌ | ✅ |

### 结论

1. **零登录方案可行**，但需要解决风控问题（Cookie 必须真实有效）
2. **登录方案更好**：
   - 解决风控问题
   - 解锁收藏夹功能（用户需求）
   - 与酷狗登录体验一致

### Bili Music 项目（2026-05-04）

**技术栈**：
- Flutter 3.11+ / Dart 3.11+
- just_audio + audio_service（播放）
- Dio + Cookie Jar（网络）
- Hive + Drift（存储）

**核心发现**：

1. **WBI 签名机制**（我们的代码里缺失！）
   ```dart
   class WbiSigner {
     // 从 Bilibili 获取密钥对
     Future<WbiKeys> fetchKeys() async { ... }
     
     // 对请求参数进行签名
     String sign(Map<String, dynamic> params, WbiKeys keys) {
       final mixinKey = _getMixinKey(keys);
       params['wts'] = DateTime.now().millisecondsSinceEpoch ~/ 1000;
       final sorted = params.entries.toList()
         ..sort((a, b) => a.key.compareTo(b.key));
       final query = sorted.map((e) => '${e.key}=${e.value}').join('&');
       return md5.convert(utf8.encode(query + mixinKey)).toString();
     }
   }
   ```

2. **Cookie 与设备指纹**
   - 自动生成 buvid3、buvid4（我们已实现）
   - **SESSDATA 导入**（登录凭证，我们不需要，但搜索可能受风控影响）
   - Cookie 持久化（我们缺失）

3. **音频流防盗链**
   - 必须设置 `Referer: https://www.bilibili.com/`（我们已实现）

4. **关键经验**
   > "Bilibili API 的不稳定性：Bilibili 的非公开 API 随时可能变更，需要做好接口版本化封装、优雅的错误降级、关键数据的本地缓存兜底。"

### 我们的代码缺失了什么？

| 功能 | 我们 | Bili Music | 状态 |
|------|------|------------|------|
| buvid3/buvid4 | ✅ 实时获取 | ✅ 自动生成 | OK |
| Cookie 持久化 | ❌ 缺失 | ✅ cookie_jar | 需补 |
| **WBI 签名** | ❌ **缺失** | ✅ **有** | **关键！** |
| Referer 校验 | ✅ 已实现 | ✅ 已实现 | OK |
| SESSDATA（登录） | ❌ 无需 | ✅ 支持 | 不需要 |

### 结论

**问题根因可能是**：缺少 **WBI 签名**。

之前报告（2026-07-15）说搜索不需要 WBI，但 **B站可能升级了风控策略，现在搜索也需要签名了**。
