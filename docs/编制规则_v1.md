> 适用范围：米豆音乐项目（midou-music）
> 本文件是项目最高工程规范，所有开发活动必须遵守。

## 0. 骨架原则（技术选型最高准则）

### 0.1 选最粗腿

技术栈选型，按以下优先级：

1. **用户量最大** — GitHub stars、npm 下载量、社区活跃度
2. **官方文档最全** — 有官方教程、有 project-structure 文档、有 create 脚手架
3. **积淀最深** — 发布 2 年以上，有大量生产案例

不自行发明技术组合。

### 0.2 用官方骨架，不自己搭

- **第一步**：用官方脚手架生成项目（如 `create-tauri-app`）
- **第二步**：阅读官方 `project-structure` 文档，逐文件理解其作用
- **第三步**：在官方骨架上加自己的代码，不改动官方生成的文件结构
- **禁止**：在官方骨架之上插入中间层（如 Tauri 上加 warp HTTP、IPC 外套 HTTP）

### 0.3 两个官方骨架之间的衔接

当需要跨技术栈协作时：

```
Tauri 官方骨架（src-tauri/src/lib.rs）
  → Tauri 官方通信方式（#[tauri::command] + invoke()）
    → 调用我们的平台适配器（platform/kuwo.rs）
      → reqwest 官方 HTTP 客户端 → 酷我 CDN
```

每一步都能在官方文档中找到对应章节，没有"我们自己发明的中间层"。

### 0.4 为什么

- 旧项目音楽自由的根本问题：在 Tauri IPC 之上加了 warp HTTP 层 → 端口冲突、CSP 报错、build 缓存地狱、调试链路翻倍
- 官方不推荐的东西，后期一定出问题
- 越简单的骨架越不容易推倒重来

### 0.5 本项目的技术栈骨架

```
Tauri v2（create-tauri-app, Vue+TS 模板）
│
├── 前端: Vue 3 + TypeScript + Vite
│   └── 通信: @tauri-apps/api invoke()
│
└── 后端: Rust (src-tauri/)
    ├── main.rs         ← 官方生成，不动
    ├── lib.rs          ← #[tauri::command] 全部写这里
    └── platform/       ← 我们自己的代码
        ├── kuwo.rs     ← 酷我适配器
        ├── kugou.rs    ← 酷狗适配器
        └── bilibili.rs ← B站适配器

没有 warp，没有 HTTP 路由，没有 8899 端口。
<audio> 标签直接播酷我 CDN URL，不经代理。
```

## 1. 功能地图（ARCHITECTURE.md）

### 原则
- 项目根目录必须有 `ARCHITECTURE.md`，用 Mermaid 图描述每个组件及其关系
- 组件粒度：一个文件 = 一个组件节点
- 每个节点标注：文件名、输入类型、输出类型、依赖列表
- **任何代码修改前**，先在地图上找到对应节点，确认影响范围
- 地图随代码同步更新，不得滞后

### 地图格式示例
```
[kuwo.rs] ──search(keyword,page)──▶ Vec<Song>
          └──play_url(song_id)────▶ String(url)
          依赖: reqwest, serde, PlatformPlugin trait

[routes.rs] ──GET /api/search──▶ warp::Filter
            └──/api/play     ──▶ warp::Filter
            依赖: kuwo.rs, kugou.rs, bilibili.rs
```

## 2. 接口定义（Top Comment 必填）

### Rust 模块
每个 `.rs` 文件开头必须包含：

```rust
// ════════════════════════════════════════════════
// 模块名: kuwo
// 路径: src/platform/kuwo.rs
// ────────────────────────────────────────────
// 功能: 酷我车载 API 适配器
// 输入: Client, keyword: &str, page: usize
// 输出: Result<Vec<Song>, PlatformError>
// 依赖: reqwest, serde, crate::platform::PlatformPlugin
// 测试: tests/kuwo_test.rs
// 接口: impl PlatformPlugin for KuwoPlugin
// ════════════════════════════════════════════════
```

### 前端组件
每个 `.vue` / `.js` 文件开头必须包含：

```js
/**
 * 组件: SongList.vue
 * 功能: 搜索结果列表展示
 * props: { songs: Song[], source: string }
 * emits: ["play", "add-to-queue"]
 * 依赖: stores/player.js
 */
```

## 3. Git 规范

### 分支策略
| 分支 | 用途 | 规则 |
|------|------|------|
| `main` | 稳定版 | 始终可编译可运行，只接受通过审查的 PR |
| `develop` | 开发主分支 | 合并 feat/x bugfix/x |
| `feat/<功能>` | 新功能 | 1-3 个文件，完成后 PR → develop |
| `bugfix/<问题>` | 修复 | 单文件，附复现步骤 |
| `legacy` | 旧代码存档 | 只读，不修改 |

### 合并规则
- 每个 PR 必须附带：改了什么 + 为什么改 + 如何验证
- 合并前 `cargo check && cargo test` 和 `npm run build` 必须通过
- 不直接 push main

### 提交信息格式
```
<type>: <简短描述>

<详细说明（可选）>
```

type 取值：`feat` `fix` `refactor` `docs` `test` `chore`

## 4. 最小可验证单元（MTU）

### 原则
- 新组件交付前，**必须**在隔离环境中独立验证
- 不能依赖完整应用启动和手工点击
- 验证通过后才能接入主应用

### Rust 模块验证
```bash
# 搜索模块
cargo test kuwo_search

# 或用独立测试脚本
cargo run --example kuwo_search -- "周杰伦 晴天"
```

### 前端组件验证
- 独立 HTML 页面 → 浏览器直接打开 → 验证渲染 + 交互
- 验证通过后 → 接到主页面

### 歌词窗口验证（典型案例）
```
test-lyrics.html   → 独立页面（绿色背景）
                  → curl 127.0.0.1:8899/test-lyrics.html 确认返回正确
                  → Tauri 独立 WebView 加载 → 验证拖动/按钮/主题
                  → 验证通过 → 替换为正式 LyricsWindow.vue
```

## 5. 不憋大招

| 规则 | 说明 |
|------|------|
| 一天最多动 3 个文件 | 超过 3 个 → 拆分任务 |
| 每次改动可回滚 | git commit 粒度 = 一个可独立验证的改动 |
| 走不通就扔 | 如果一条路径改了 3 次还不通 → 换方案，不回滚地硬调 |
| 先验证后合并 | 独立测试通过的代码才允许合并到 develop |
