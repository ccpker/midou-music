## 根因分析

### 直接原因
rodio `Sink` 创建后默认是 `paused` 状态，需要显式调用 `sink.play()` 才能播放。

### 为什么 minitest 有声，v2 无声？
- minitest 的 `_stream` 和 `sink` 在同一个作用域，生命周期简单
- v2 的 `_stream` 被包在 `Player` 结构体里，生命周期被 Tauri 管理

但真正的原因是：**v2 的 `sink.play()` 没有被调用**。

### 为什么之前的修复没生效？
15:44 加了 `sink.play()`，但 15:47 测试时日志显示下载完成就停了 —— **Player 线程卡在 `play_bytes` 入口之前**。

原因：**修改代码后没有正确重新构建**（可能是 WebView 缓存、可能是 cargo 增量构建问题）。

15:50 加了详细日志（`play_bytes 入口`、`开始解码`、`解码成功`），强制重新构建后，所有日志都出来了，声音也有了。

## 关键教训

### 1. 最小功能单元排查法（米豆方法论）

```
问题现象
  ↓
定位到最小功能单元（一个文件 / 一个函数 / 一个模块）
  ↓
隔离运行该单元（脱离主流程单独验证）
  ↓
确认根因（不是猜测，是验证）
  ↓
修复该单元
  ↓
验证该单元（通过后再回归主流程）
```

这次用 minitest 隔离验证 rodio 本身是否正常，是关键转折点。

### 2. 日志要打到"入口"而非"成功后"

之前日志只打 `playback started`，但如果 `play_bytes` 入口都没到，日志就停在上一步。

**修复后日志**：
```
[15:54:07.355] [midou-audio] 下载完成 10588143 字节
[15:54:07.355] [midou-audio] play_bytes 入口: 10588143 字节  ← 入口日志
[15:54:07.361] [midou-audio] 开始解码...
[15:54:07.362] [midou-audio] 解码成功
[15:54:07.362] [midou-audio] playback started
[15:54:07.463] [midou-audio] sink empty=false, len=1, paused=false
```

### 3. 构建缓存会骗人

15:44 的修改，15:47 测试时没生效 —— **cargo 增量构建 + WebView 缓存 + 文件写入延迟**，任何一个环节都可能让修改"看起来没生效"。

**对策**：
- 修改后立刻看日志是否有新的标记（如 `play_bytes 入口`）
- 如果没有，说明构建没更新，需要强制 rebuild

### 4. rodio 的坑

rodio `Sink` 创建后默认 `paused=true`，必须显式 `sink.play()`。

这不是 bug，是设计（允许预先 append 多个 source，然后一起播放），但文档没强调这一点。

## 技术栈对比

| | v1（WebView audio） | v2（rodio Rust 原生） |
|---|---|---|
| 音频引擎 | 浏览器 `<audio>` | Rust rodio |
| 自动播放限制 | ❌ 受限（首次需点两次） | ✅ 无限制 |
| 音频上下文解锁 | 需要用户手势 | 不需要 |
| 跨平台 | 依赖 WebView 实现 | 纯 Rust，一致性强 |
| 可控性 | 浏览器 API 有限 | 完全控制（解码、混音、特效） |
| 调试难度 | 高（浏览器黑盒） | 中（Rust 日志清晰） |
